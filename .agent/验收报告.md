## 二十一项改进

### 🔴 最严重的四个

#### ① 七维里有两维在空转

**实测**：36 条真实案例里

| 维度 | 识别不出类别 | 后果 |
|---|---|---|
| `constraint_match` | **20/36（56%）** | 固定返回 0.5 |
| `goal_match` | **29/36（81%）** | 固定返回 0.5 |

「结构化匹配 7 个维度」是产品核心主张，但 **28.6% 的信号是空的**。

**改法**：按真实数据扩词典（约束 6→11 类，目标 5→10 类）+ 类别识别不出时用字符 bigram 兜底。

| 指标 | 改前 | 改后 |
|---|---|---|
| 空转率 | 68% | **19%** |
| 有效维度数 | 5.6 / 7 | **6.6 / 7** |

---

#### ② What-if 是个悬空承诺 → 变成演示杀器

**实测**：后端在 **24 条反类比里有 9 条（37.5%）** 写着「你可以在 What-if 里补充信息再看匹配变化」——**但功能不存在**。

**它更大的价值**：这是**证明「结构匹配而非文本匹配」的唯一硬手段**。文本相似度不会因为你「假设不怕延毕」而改变，结构匹配会。

**改法**：新增 What-if 面板（4 个预置假设 + 自定义输入）。刻意不调 LLM 解析自定义条件（那要多 2-3 秒，而价值就在即时看到结构变化）。

**实测**：

```
原始            → 拉马克里希南 / 爱因斯坦 / 李安
假设经济压力大   → 爱因斯坦 / 考里科 / 拉马克里希南     ← 三个人全换
```

**刻意不走离线降级**：降级返回固定快照，「改条件→结果变化」就成了假的。

#### ③ 我自己引入的回归

加「按人去重」时读了 `person.name`，而验收脚本会传 `episode: undefined` 的条目 → 崩。
**旧实现只读 `choice.type` 所以一直没暴露。** 已修 + 加测试钉住。

#### ④ 「止损止损」清了两次都没清掉

第一次修：后端解析阶段加净化 —— 只处理「整串重复」和「空格分隔重复」。
第二次修：会话恢复时也净化 —— 同逻辑，同样无效。

**真正的问题形态是句子中间的重复**：

```
【目标】在意的目标有具体交集：「止损止损」（对方的目标：…）
```

重复发生在句中，不是整串。两次修都没覆盖到。

**改法**：改成滑动窗口（长窗口优先），处理任意位置的相邻重复。
并给中文合法叠词（好好/慢慢/偏偏）加白名单，否则「好好想想」会被删成「好想想」。

**附带补漏**：会话恢复时原来只清 `situation`，**没清 `result`** ——
而坏文本恰恰在 `result.matches[].why_similar` 里。同一类问题我只覆盖了一半。

### 🟢 按数据可信度做的

#### ⑭ 来源链接体检（`npm run check:sources`）

`data/REVIEW.md` 写着「人类审核尚未完成」，这是最大的剩余风险。
AI 不能代替人确认「claim 与来源一致」，但**能查链接打不开** —— 而那恰好最容易当场出丑。

**查出的真问题**：2 条死链
- `LX-MUSEUM` → **404**（官网改版）→ 改到场馆首页并在 limitations 写明
- `EY-BIO` → Akamai 全拒，无法自动核查 → 保留一手来源，写明核查路径

**工具本身踩的坑（已修）**：第一版用自定义 UA，dyson.com 返回 403 被报成坏链；
换浏览器 UA 就是 200。**误报比不报更糟** —— 会让人去"修"没坏的东西。
所以区分「反爬」与「真挂」，并维护一份写明原因的 `KNOWN_BOT_WALLS` 清单。

结果：**❌ 确认有问题 0**，🔒 需人工确认 7，✅ 可达 29。

#### ⑮ 人工核查清单（`npm run review:sheet`）

「去审一下来源」太模糊：没人知道从哪开始、做到什么算完，结果是它一直不开始。

**改法**：生成 `data/REVIEW-CHECKLIST.md` —— 36 条来源 / 63 条 claim 摊成可打勾的表：
每条给出机构、链接、文献定位、已知局限，以及**它具体支撑哪些 claim**（精确到原句）。

把开放式任务变成有界清单：**36 行 × 每行约 30 秒 ≈ 20 分钟能过完，进度可数。**

> 脚本只生成清单，不判断内容。「原文是否支持这句话」必须人读 —— 工具不假装能做。

#### ⑯ 证据抽屉加上可点击链接

抽屉的整个承诺是「每个关键事实都能追溯到具体来源」，
但原来只显示 `source_id`（如 `LX-SENDAI`）—— **最需要"点一下验证"的地方，什么也点不了。**

数据里本来就有 `url`，只是没渲染。现在：
- 有 url → 「打开原文 ↗ dyson.com」（新窗口 + `rel=noreferrer`）
- 无 url 的 AI 推断 → 「AI 建模产物，无外部来源」（而不是留空白让人以为漏了）

**把「我们号称可追溯」变成了「你自己点开看」。**

#### ⑰ 原子化的快照刷新

实测撞到：`demo1` 是 05:13、`demo2/3` 是 05:05 —— refresh 第二个 demo 失败就 `exit(1)`，
留下「一半新一半旧」。而 preflight 只看最新那个 mtime，**会误判成"快照是新的"**。

**混着两代数据的快照比全旧更危险，因为看不出来。**

改法：refresh 改成「先全部取回、确认都成功、再统一落盘」；
preflight 新增「三份离线快照是同一批生成的」检查（比对 mtime 差值）。

## 第三轮：把「看起来像数据」的地方真的变成数据

### ⑱ 分叉地图的「过去」是写死的占位词

**实测**：无论用户输入什么，地图上都显示同样的「入学 / 投入 / 动摇」。
把处境改成「工作五年、做产品」，地图上照样写「入学」。

而这张图**占了整整一屏**，是整个 demo 视觉上最显眼的东西。
写死的标签等于当面告诉评委：**这张图是装饰，不是数据** ——
这跟「匹配靠结构、靠数据」的主张直接冲突。

**改法**：三个节点从真实数据推
- 起点 ← `situation.stage`
- 中段 ← 匹配案例 `prior_path` 里 **≥2 个案例共有**的短词
- 末段 ← 固定「动摇」（能走到检索这一步，对所有处境都成立）

| 输入 | 节点 |
|---|---|
| 大三，材料科学 | `大三本科中` / `已投入` / `动摇` |
| 工作五年，做产品 | **`职业发展中`** / `已投入` / `动摇` |

---

### ⑲ P1 的引导问题只有校园版

**实测**：产品自己准备的第三个演示场景是「大厂还是小厂/创业」—— 一个职场处境。
但 P1 六问的 placeholder 全是校园场景：

> 「过去**两年**你主要在做什么？」「**专业课 + 实验室**打杂，参加过两次**竞赛**」

评委试那个场景时会看到一堆只在大学里成立的问题，
立刻露出「这套东西只做过学生」的马脚。

**改法**：按处境分三套措辞（校园 / 职场 / 中性），判不出来就退回中性、不假装知道。

改后第 2 问（输入「工作五年」）：
> 「**这几年**你主要**积累**了什么？」「三年 to B 产品经验，带过两个人，没做过从 0 到 1」

---

### ⑳ 超出产品范围的输入会被硬编成处境

**实测最尴尬的一条**：

```
输入「今天中午吃什么好呢，食堂人太多了」
→ 阶段=午餐决策，冲突=忍受拥挤 vs 另寻出路
→ 认真匹配出 布赖恩·梅 / 詹姆斯·戴森 / 斯图尔特·巴特菲尔德
```

**系统一本正经地拿三位历史人物对照这顿午饭。**
这比「我处理不了」难看得多 —— 它暴露的是「模型在硬编」。

同类：`买哪个手机好` / `今天天气怎么样` / 单字 `烦`（被解析成「情绪爆发期」）。

**改法**：加 `detectOutOfScope()` → API 返回 **422 OUT_OF_SCOPE** →
前端**不导航、不降级**，在原页给出引导：

```
⚠️ 这个系统处理不了这类问题
   这是日常消费选择，不是人生抉择。
   这里找的是「和你走到过相似人生节点的人」，不是帮你决定这顿吃什么。
   [好，我换个说法]
```

刻意保守：**宁可少拦，不要误拦**。判不准就交给模型 ——
拦错真实处境比放行一句玩笑话更伤。

实测 10 组：拒答 6 组全对，放行 4 组全对（含「很迷茫」这类短但真实的表达）。

## 第四轮：专找「数字和版式在骗人」的地方

前三轮修的是坏掉的东西，这轮专找**「看起来对、其实在误导」**的 —— 评委一读就得出错误结论。

### ㉒ 检索耗时少报了 8 倍

P3 显示「耗时 0.3s」，但那是 `meta.elapsed_ms` —— **只有检索那一段**。

| 场景 | UI 显示 | 用户实际等待 | 少报 |
|---|---|---|---|
| demo1 | 0.3s | 2.6s | 8.8× |
| demo2 | 0.2s | 2.9s | **16.6×** |
| demo3 | 0.4s | 3.7s | 9.0× |

解析（2.3–3.3s）**完全没计入**。而这块区域正上方写着「我们不隐藏过程」，
最显眼的数字却在藏 90% 的时间。评委一边等三秒、一边看到「0.3s」，
只会觉得这个数字是挑出来的。

**改法**：报**用户实际等待**的合计，并拆开说明慢在哪：

```
本次耗时 3.2s
其中：理解你的处境 2.8s　检索与重排 0.4s
（不含网络往返；数据越多、这步越慢）
```

---

### ㉓ 维度卡里「差异惩罚」的条方向是反的

七条维度里，前六条「越高越像」，第七条「差异惩罚」是**越高越不像** ——
却用同一种条长表达。扫一眼会读出：

```
差异惩罚 ██████████████████ 90%   ← 看起来「很好」
```

而它恰恰是「不能照搬」的核心指标。

**改法**：翻转成「**可迁移性**」= 1 − 惩罚，让**七条方向统一：条越长越好**。

| 惩罚 | 改前条长 | 改后条长 |
|---|---|---|
| 0.90 | 90%（像好事） | **10%（正确表达"几乎不能套用"）** |
| 0.55 | 55% | 45% |

并按档位给解释：≥0.75「**结果**几乎不能套用」/ ≥0.45「参考**做法**，别照搬**结果**」。

---

### ㉔ 三条路的展示顺序其实是排名

前端标成 路径 A / B / C，A 在最上面。后端 `picked` 是**按分数降序**的 ——
实测三个场景里 **A 永远是最高分那条**。

页面嘴上说「不是排名，也不是推荐」，**版式却在排**。
而「不替你做决定」正是产品的核心主张 —— 一个隐含排序等于偷偷做了决定。

**改法**：按 `episode_id` 的稳定哈希打散展示顺序（确定性 + 与分数无关）。

| 场景 | 最高分在哪 |
|---|---|
| demo1 | 路径 C（第 3 位） |
| demo2 | 路径 B（第 2 位） |
| demo3 | 路径 A（第 1 位） |

并在页面上写明「顺序是刻意打散的」。

### ㉕ 文案红线自动检查

「不给处方」是最容易被后人无意破坏的一条 ——
随手加句「建议你先做低成本验证」，产品调性立刻就变了。

后端已有 output-guard 拦模型输出，但**写死在前端代码里的文案**没人管。

**改法**：preflight 加第 9 项，扫 `src/**` 的用户可见文案，
命中 `你应该 / 建议你 / 我推荐你 / 最优选择 / 正确选择` 即阻塞并指出行号。

**变异测试**：插入「建议你选择第一条路」→ ❌ 抓到 `P5Compare.tsx:36` ✅

**同时巡检现状（都干净）**：
- 前端用户可见文案：无指令性表述 ✅
- 三个场景生成的反类比：无指令性表述 ✅
- 三个场景各覆盖 3 种 `choice.type`，「覆盖不同选择方向」的说法成立 ✅

## 第五轮：把「归属错了」的信息改回来

这轮专找**「系统把功劳或内容算在用户/自己头上」**的地方 —— 说得比实际做到的更多。

### ㉖ 「看证据来源（N）」把 AI 推断也算成了来源

P4 的按钮用的是 `ep.evidence.length`。但**每条案例的 evidence 里都有 1 条 `ai_inference`**
（说明哪些字段是建模出来的，**不是来源**）。

| 案例 | 按钮显示 | 实际能点开 |
|---|---|---|
| 李安 | （3） | **2** |
| 纽斯莱因-福尔哈德 | （2） | **1** |

**点进去发现少一条，比一开始就写对更伤可信度** ——
尤其这个按钮存在的意义就是「让你能验证」。

**改法**：按钮只数外部来源；抽屉把两类分开说清：

> 这条案例有 **2 条外部来源**（其中 2 条可直接点开原文）。
> 另有 **1 条 AI 推断** —— 那不是来源，只是说明哪些字段是建模出来的，不必去找出处。

---

### ㉗ 全跳过 6 问时，把系统编的处境说成「从你的回答里抽出来的」

用户一个字都不填、一路点「下一个问题」时，前端会把一句兜底文案
（「我想换个方向，但不确定该不该换。」）发给后端。

后端据此**编出完整处境卡**（实测）：

```
阶段：方向抉择期
冲突：维持现状 vs 更换方向
约束：已有沉没成本、切换有阻力
目标：确定新方向、减少迷茫
```

而 P2 写着「**我们从你的回答里抽出了这些结构**」——
**把系统编的内容算在用户头上。**
评委连点六次「跳过」就会看到这个，而且看到的还是自己的"回答"。

**改法**：按「有没有真的写过」分两种措辞。

| 情况 | 措辞 |
|---|---|
| 有输入 | 「我们从你的回答里抽出了这些结构」（保留原文案） |
| 全跳过 | 「**你没有填写任何内容** / 下面是一份**通用起点**，不是从你的话里读出来的 / **把它改成你自己的处境**，后面的案例才会真的像你」 |

## 第六轮：让证据真的能核查

### ㉘ 抽屉只显示一个编号，而「可核查」需要的是「谁说的、在哪一段」

`data/sources.json` 里其实有 `publisher` / `title` / `locator` / `accessed_on` / `limitations`
—— **这些正是让证据可核查的东西**。但 `episode.evidence` 只带 `source_id` + `url`，
**前端根本拿不到**。

| | 改前（抽屉里） | 改后 |
|---|---|---|
| 来源 | `LX-SENDAI` | **澎湃转载楚尘文化《李安访谈录》** |
| 定位 | — | **格伦·肯尼访谈：毕业后六年、1990 年剧本比赛、推手** |
| 局限 | — | **中文译编的事后访谈；未将六年没有执导机会扩大成六年无任何正式工作** |
| 访问日期 | — | **2026-10-02** |

**注意那条「已知局限」** —— 那是 fu6868 在数据里**主动写下的防过度解读提示**。
原来它只躺在 JSON 里，现在直接摆给用户看。

**这正是产品主张的那种智力诚实：连「我们的表述可能过头了」都摆出来。**

实现：`loadSourceMeta()` 读 sources.json → `retrieve()` 把 `source_meta` 放进响应 →
契约加 `SourceMeta` → 抽屉渲染。

> 也考虑过把 publisher 冗余进每一条 evidence，否决了：
> 99 条 evidence 会重复存 37 份出版信息，改一处要改多处，
> 而 sources.json 本来就是唯一来源。

## 第七轮：把真正拖慢体感的那一段找出来

### ㉙ 解析占了 87% 的等待，而我一直只在优化那 13%

量了一下各段耗时：

```
demo1  墙钟 3.3s  |  解析 2853ms  |  检索 395ms
demo2  墙钟 2.9s  |  解析 2748ms  |  检索 173ms
demo3  墙钟 3.6s  |  解析 3380ms  |  检索 157ms
```

**解析占 87%，检索只占 13%。**
也就是说：我前面给检索做的那些优化（预热索引 2.6s→0.38s 等），
只影响那 13% —— **真正决定评委体感的是解析这一段，而它一直没被碰过。**

**改法**：换掉解析用的模型。同一提示词 + `json_schema`，三个场景各跑 3 轮（共 9 次）：

| 模型 | 成功 | 平均 | 中位 | 最慢 |
|---|---|---|---|---|
| `glm-5` | 9/9 | 4.1s | 4.0s | 5.4s |
| **`deepseek-v4.1-flash`** | **9/9** | **2.3s** | **2.2s** | **2.8s** |

快 44%，成功率一样，输出质量不降。

**端到端效果**：

| 场景 | 改前 | 改后 |
|---|---|---|
| demo1 | 3.3s | 3.2s |
| demo2 | 2.9s | **1.8s** |
| demo3 | 3.6s | **1.6s** |
| **平均** | **3.3s** | **2.2s** |

省下的 1.1 秒是评委直接能感觉到的。

**可回退**：模型名抽成 `SITUATION_MODEL` 常量，支持环境变量覆盖 ——
现场万一新模型出问题，`SITUATION_MODEL=glm-5 npm run server` 一条命令换回去。

**顺带记录几个试过但不可用的**（免得后人重复踩）：

| 模型 | 问题 |
|---|---|
| `glm-5.3-flashx` | 该模型始终思考，关不掉（400） |
| `glm-4.5-air` | 只支持 stream 模式 |
| `glm-5.3` | 空 content（输出全在 reasoning） |
| `qwen3.5-flash` | `json_schema` 模式下要求提示词含 "json" 字样 |
| `step-3.7-flash` | 空 content |
| `minimax-m3` | 14.4s，且返回非法 JSON |

> **教训**：优化要看占比，不要看哪块代码眼熟。
> 我在那 13% 上花了好几轮，而 87% 那块一次都没量过。

## 第八轮：先把性能量清楚，再修文档

### ㉚ README 严重过期 —— 照着做会得到坏掉的环境

先按上一轮的教训**量了一遍性能**（不再凭感觉优化）：

```
/api/consult   1.6-1.9s   （解析 1.3-1.6s + 检索 0.25-0.29s）
What-if 单次   0.17-0.31s （连点 4 次实测）
20 次连续调用  0 失败，中位 1.48s，最慢 1.67s
→ 性能和稳定性都够了，不必再优化。转去看别的。
```

然后看文档，发现 **README 是 5.2 小时前写的**，早于所有改动：

| 问题 | 后果 |
|---|---|
| 快速开始写 `npm run dev` | 它**只启前端、不带后端** —— 照做的人看到接口全失败、页面静默走离线兜底，却不知道哪错了 |
| 常用命令只列 3 条 | package.json 里实际有 13 条 |
| What-if / preflight / check:sources / review:sheet **完全没提** | 这一轮加的整套验证工具，队友和评委都不知道存在 |

**文档过期比没文档更坑：没文档人会问，过期文档人会照做。**

**改法**：
- 快速开始改成 `npm start`（一条命令拉起前后端）+ 补 `npm run preflight`
- 命令表拆成「演示/日常」与「数据/验证」两张，13 条全覆盖
- 新增「演示相关的两个关键设计」：What-if 为什么是杀手锏、离线兜底怎么工作
- 技术要点补上模型切换（含回退方式与 6 个不可用模型）、embedding 批量上限

**防复发**：preflight 新增第 10 项，比对 README 写的命令与 `package.json` ——
写了不存在 → 阻塞；实现了没写 → 也提醒。

> **变异测试抓到了我自己的 bug**：第一版正则用 `[a-z:]+`，
> 脚本名里的连字符没进字符类，于是 `preflight-typo` 会被截成 `preflight` —— **漏报**。
> 把 `-` 加进字符类后才抓住。

## 第九轮：脚手架残留，以及一个让验证本身不可靠的坑

### ㉛ favicon 一直是 Vite 自带的紫色 logo

`public/favicon.svg` 从来没人动过 —— 它是 `create-vite` 自带的图标：
**9522 字节、主色 `#863bff`（Vite 紫）**，和本产品毫无关系。

评委打开标签页看到的是一个 **Vite 图标**。小，但属于典型的「没做完」信号，
而且出现在最显眼的地方（浏览器标签）。

**改法**：换成产品自己的图标 —— 分叉地图的极简版：

- 左边一条实线 + 两个节点 = 已经走过的路（过去）
- 中间一个实心点 = 现在站的路口
- 右边三条分叉 = 别人走出的不同方向（最后一条透明度 0.72，呼应「未来是迷雾」）

配色直接取 `src/styles.css`。体积 **9522 → 1442 字节**。

---

### ㉜ public/icons.svg —— 第二个残留，无人引用

顺着 favicon 扫了一遍 `public/`，发现 **5031 字节的 `icons.svg`**，
来自最初的脚手架提交，内容是 bluesky 等社交图标，**代码里零引用**。

它会随构建一起发出去，白涨体积，也是「没做完」的信号。已删除。

**preflight 第 11 项扩成两条**：
- favicon 不得是脚手架图标（特征色检测 + 体积异常提示）
- **`public/` 下任何文件都必须被 `src/` 或 `index.html` 引用**，否则判死文件

### ㉝ dist 从不清空 —— 让「验证构建产物」这件事本身不可靠

这是本轮最有意思的发现：修完 `icons.svg` 后我看构建产物，
**发现 `dist/icons.svg` 还在** —— 而它已经从 `public/` 删掉了。

一查：Vite 默认**没有**清空 `outDir`。连构建 11 次后 `dist/` 里堆了：

```
11 个历史 index-*.js / *.css（每次构建一个）
+ public/icons.svg 的陈旧副本
+ 我变异测试时塞进去的 dead-file.svg
```

**后果不是磁盘占用，而是验证不可靠**：
你想确认「新代码有没有进产物」，翻到的可能是上一次的构建结果。
> 这一轮我差点又被误导一次 —— 差点以为 `icons.svg` 还在源码里。

**改法**：`vite.config.ts` 显式打开 `build.emptyOutDir: true`。

实测连续构建 3 次，产物稳定在 4 个文件。

> **这也说明了前几轮的一个盲区**：我用 `ls dist` 看产物时，
> 看到的可能一直是陈旧的累积结果 —— 只是没碰到需要精确比较的场景而已。

## 第十轮：补上最大的盲区 —— 页面到底有没有渲染出来

### ㉞ 18 项检查都在查「文件在不在」，**没有一项知道页面长什么样**

我盯着 preflight 的检查清单看了一会儿，发现一个结构性缺陷：

| 已覆盖 | 未覆盖 |
|---|---|
| .env 在不在 | **前端有没有运行时错误（白屏）** |
| 数据条数够不够 | **页面元素有没有真的渲染出来** |
| 快照在不在、新不新 | **6 条路由是不是都能打开** |
| 构建能不能过 | **演示流程走不走得通** |
| 单测、lint、数据校验 | **断网降级是不是真的生效** |

**一个 JS 运行时错误可以让「构建通过 + 单测全绿 + 快照齐备 + 中文不乱码」
同时为真，而评委看到的是白屏。** 这是最容易翻车、又最不容易被现有检查发现的一类。

### 改法：`npm run smoke` —— 真实浏览器冒烟

不引入 puppeteer/playwright（多几十 MB 依赖），
直接用系统已装的 **Chrome/Edge，经 CDP（DevTools Protocol）** 驱动。

查什么：
- 6 条路由都能打开，且渲染出各自**独有**的标志性文字
- 控制台没有 error / 未捕获异常
- 页面有实质内容（不是空白）
- 顺带确认前端真的连得上后端接口（而不是一直在走离线兜底）

### ⚠️ 第一版有洞，是变异测试抓出来的

第一版**没种会话状态**，于是 P2–P6 全部只渲染「还没有检索结果」的空状态 ——
**真正要验的那几百行渲染代码一行都没执行**。

证据：我在 P5 里埋了一个必然抛错的表达式，第一版报告「6 条路由全部渲染正常」。
（空状态在渲染出错那一行之前就 `return` 了。）

**修法**：进页面前先调 `/api/consult` 拿真实数据种进 sessionStorage，
并要求「需要状态的页面不得掉进空状态」。

修完再测同一次变异：

```
❌ P5 像与不像   页面几乎是空白（只有 0 字）
   控制台错误：Error: smoke-test-injected
❌ 1/6 条路由有问题        exit=1
```

**改前漏报，改后抓住** —— 这才叫检查。

### 接入 preflight

作为第 17 项。只在后端在跑时才做（冒烟需要后端提供真实数据），
后端没起时标为非阻塞提醒并说明原因。

### 顺带：README 项数一致性检查（并踩了一次自己的坑）

写完这项后我自己就把 README 的项数写错了（写 16，实际 17）。
于是又加一项：**README 里写的自检项数必须等于脚本里的 `check(` 调用数**。

第一版用 `results.length + 1` 算，off-by-one；改成数源码里的调用数才对。
现在是 **18 项**。

## 第十一轮：demo 的保险绳，第一次被真正验过

### ㉟ 断网兜底：反复承诺，但从没验过

方案验收清单第 11 条写的是「**断网/API 错误时有缓存的 Demo 数据，保证上台可演示**」。
DEMO.md、README、这份报告里都反复承诺这一条。

**但在这之前，我们只验过「快照文件在不在、场景数够不够」。**
从没验过：后端真挂掉时，前端到底会不会降级？降级得对不对？

> 这是 demo 的**保险绳**：只在断网那一刻才用得上，平时跑不到那条路径。
> 而它恰恰最不能临时抱佛脚。

**做法**：起一个**把 `/api` 代理到 `127.0.0.1:1`** 的临时前端实例，
用真实 Chrome 走一遍 P1→P2→P3，验 6 件事。

**结果：兜底本身是对的。**

```
✅ 接口确实不可用（HTTP 502 —— 前提成立）
✅ 后端全挂时 P1→P2 仍能走通（不白屏、不卡死）
✅ 出现「离线演示模式」横幅
✅ 横幅明确说明「不是实时计算结果」
✅ 降级到与输入匹配的场景 —— 输入写考研，降级也给「考研 vs 工作实习」
✅ P3 / P5 仍能渲染快照数据
```

---

### 排查时挖出的三个真问题（都在我自己的代码里）

**① `.env` 里的 `VITE_API_BASE` 让代理形同虚设**

`.env` 配了 `VITE_API_BASE=http://localhost:3000`，前端 fetch 的是**绝对地址、绕过 Vite 代理** ——
于是「把代理指向死端口」根本拦不住请求。第一次跑时**页面拿到了实时数据，而测试以为已经断网**。

> 顺带暴露：`vite.config.ts` 里我早先为「前端连后端」加的 proxy，
> 在配了 `VITE_API_BASE` 时**其实没被用到**。两条路径行为不一致，而我只测过一条。

**② 我的判定写错了**：只 `try/catch fetch`，但代理到死端口时 Vite 回的是 **HTTP 502**，
`fetch` 并不抛异常 → 误判成「接口是通的」。必须同时看状态码。

**③ 点击计数不可靠**：第一版固定点 6 次以为到最后一问，实际 React 状态更新有延迟，
几次点击被同一问吃掉 → 循环结束时早已越过，后续检查全部错位。

**改成按页面状态判断**（读「第 N / M 问」，N<M 就继续点）。

把降级逻辑改成「永远用场景 1」→ ❌ **精确命中**「降级到与输入匹配的场景」这一项。

## 踩坑记录（给自己和后来的人）

1. **PowerShell 改文件会毁掉 UTF-8**：`Get-Content -Raw` 按 GBK 读、`WriteAllText` 按 UTF-8 写，
   中文直接变乱码。这份报告本身就被毁过一次，只能重写。
   **改含中文的文件一律用编辑工具，不要用 PowerShell 文本操作。**
2. **`execFileSync('npm', ...)` 在 Windows 上 ENOENT**（npm 是 `.cmd` 包装），
   改调 `npm.cmd` 又 EINVAL。要用 `node` 直接跑真实入口。
3. **改完后端要确认进程真的重启了**：我曾在旧进程上测了半小时，结论全是错的
   （3000 端口上跑的是 1 小时前的代码）。
4. **`edit` 改文件末尾容易留下孤立注释片段**，导致解析失败 —— 已踩三次，改完必跑单测。
